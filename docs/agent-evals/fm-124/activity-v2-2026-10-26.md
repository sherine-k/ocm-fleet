# FM-124 mechanical activity comparison

These counts were replayed from the four completed v2 runs. No model sessions
were rerun. [Machine-readable results](activity-v2-2026-10-26.json) include source
paths, SHA-256 hashes, exit-code distributions, and logged command categories.

Each activity cell is **overall / before first edit**:

| Metric | Control 1 | Control 2 | Treatment 1 | Treatment 2 |
| --- | ---: | ---: | ---: | ---: |
| Model tool calls | 110 / 6 | 69 / 10 | 109 / 14 | 73 / 10 |
| Shell commands | 78 / 24 | 72 / 22 | 65 / 14 | 110 / 57 |
| Recognized skill reads | 1 / 1 | 1 / 1 | 0 / 0 | 0 / 0 |
| Nonzero shell exits | 10 / 0 | 9 / 1 | 13 / 0 | 8 / 0 |
| Frozen independent checks failed | 0 / 11 | 0 / 11 | 0 / 11 | 0 / 11 |
| Supplemental login stream check failed | 1 / 1 | 0 / 1 | 0 / 1 | 1 / 1 |

The last two rows are **failed / total checks**, measured after completion.
Both recognized skill reads were `nx-workspace`. All model tool calls were
`exec`; those wrappers batch shell commands, patches, and polling. Consequently,
tool calls and shell commands are separate metrics, not additive counts.
For example, Treatment 2 issued ten wrappers but 57 shell commands before editing.

The [activity analyzer](harness/tool_statistics.py) counts actual
`CommandExecution` events once per ID, rather than JavaScript mentions of
`exec_command`. One compound shell script counts once; its unlogged child
processes are not counted. Polling does not count as another shell command.
Read/search/list categories come directly from the logger, can overlap, and
retain `unknown`; they are not model-generated classifications.

The pre-edit window excludes the entire tool call enclosing the first successful
`FileChange` event, including any reads batched with that edit. Its mechanically
identified requests are 7, 11, 15, and 11, matching the existing checkpoint
reviews. Arbitrary shell writes are not file-watched. Missing or ambiguous
boundaries remain null. Skill reads require a successful nonempty shell command
with a logger-classified read of `SKILL.md`; indirect/unclassified reads can be
missed. Retrieval does not establish whether the model applied a skill.

Nonzero exits measure observable friction, including iterative test failures,
unmatched searches, and environment failures. They do not measure remaining
defects. The independent assessment totals are parsed from unittest/Vitest log
summaries, with job exit codes preserved; incomplete summaries are rejected.

The login helper mismatch was absent from the original check coverage. A
[supplemental static check](harness/login_stream_contract.mjs), added after all
four runs, now emits a JSON pass/fail result for that specific contract. It uses
the installed TypeScript parser to compare the directly declared stream receiving
`AUTH_URL` with the helper's `readline` input. All four writers declare stderr;
Control 1 and Treatment 2 still read stdout. The checker returns `unresolved`
for unsupported or ambiguous shapes. This is a narrow static contract check,
not an exercised browser login or a general defect count. Keep it separate from
the frozen 11-case results to make its post-hoc origin explicit.

To reproduce a run's activity data:

```sh
python3 docs/agent-evals/fm-124/harness/tool_statistics.py "$rollout" \
  --run "$name" --assessment "$assessment_directory" --output "$statistics_json"
node docs/agent-evals/fm-124/harness/login_stream_contract.mjs "$subject"
```

The second command prints one JSON result and exits 0 for passed, 1 for failed,
or 2 for unresolved. It reads subject files without modifying them and loads the
subject's installed TypeScript dependency. Its new results are saved separately
from the original sessions/assessment logs in the raw statistics directory named
in the JSON report. The report retains source hashes for this supplemental check.
No human/LLM review annotations feed these activity or check counts.
