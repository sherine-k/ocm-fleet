# FM-124: duplicate controls, October 23, 2026

Two fresh Luna Max sessions completed the same fleetctl refactor with the
original agent guidance. Control 1 used 65% more accumulated tokens and took
33% longer. Both loaded the same single skill. Control 2 passed its own checks
but failed an independent check for an unhandled stream error.

This is an A/A measurement of run variation. No altered-guidance run has been
performed, and these results do not establish the benefit of removing skills.

The follow-up [early context analysis](context-growth-2026-10-23.md) adds
per-request input sizes, instruction-retrieval checkpoints, and a method for
isolating the fixed initial contribution of guidance.

across model requests and is not peak context size or a dollar cost. The
largest reported single-request input is a separate observed usage measure.
Setup, parent analysis, and independent assessment are excluded from coding
session usage and elapsed time.

## Outcome assessment

Both sessions implemented typed runners and optional presenters, shared format
selection, direct JSON serialization, presenter-free JSON fallback, and command
migration including resource types, resource describe, and success messages.
Both moved login progress to stderr and updated the E2E helper. Both added
compile-time result/presenter coverage and updated CLI documentation.

| Evidence | Control 1 | Control 2 |
| --- | --- | --- |
| Final CLI tests | 26 passed | 26 passed |

| E2E lint and diff whitespace check | Passed | Passed |
| Independent exact JSON checks, CI=true/false | Passed | Passed |
| Independent awaited Writable completion | Passed | Passed |
| Independent real Writable failure | Passed | Unhandled error event |

The independent four-test suite used each implementation's actual output
writer and real Node Writable/PassThrough streams, outside the frozen subject
checkouts. It did not install a caller-side error listener. Control 2's promise
rejected, but Node also emitted an unhandled `error` event, causing Vitest to
exit 1. Its own error test installed a no-op listener and therefore missed the
defect. Control 1 handled the event and its independent suite exited 0.

The assessment is targeted rather than an exhaustive integration proof. No
live management backend or Podman-backed browser scenarios were exercised.
Completed commands with nonzero exit statuses remain in the raw transcripts;
these include intentional failing tests, negative type probes, unsuccessful
searches, and ordinary implementation/validation failures.

## Interpretation

Identical initial context and identical observed skill use still produced
material differences in output quality, model round trips, elapsed time, and
accumulated tokens. A single cheaper treatment run would be weak evidence of a
guidance improvement. Compare repeated runs using the same prompt and rubric,
and retain quality findings alongside usage. Concurrent execution and shared
provider caching also limit interpretation of timing and cache differences.

## Reproduction

Export the fixed source into independent repositories, prepare dependencies
equally, and run each fresh session with the same prompt and work profile:

```sh
CODEX_HOME="$HOME/.codex-work" codex --no-daemon --search --approve-for-me \
  -m gpt-6-luna -c 'model_reasoning_effort="max"' -C "$checkout" \
  exec --json --color never -o "$artifacts/final.md" - \
  < fleetctl-output-prompt.txt > "$artifacts/events.jsonl" 2> "$artifacts/stderr.log"
```

Before launching, use the same common options with `debug prompt-input` and
the prompt argument to preserve initial context. Check the rendered skill
catalogue, actual session model/effort, prompt hash, and source equality.
Preserve the final cumulative usage record rather than summing repeated
cumulative records. Keep independent assessment outside the coding sessions.
